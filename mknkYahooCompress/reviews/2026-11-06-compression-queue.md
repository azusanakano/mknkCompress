# 圧縮キューの行別レビュー

## 修正後の確認（2026年11月6日）

以下の指摘は `review-fix` 版で対応した。下段の実機検証・行番号・指摘は、修正前の記録としてそのまま残している。

| 指摘 | 修正と確認結果 |
|---|---|
| 差し替え後も古い入力容量を使う | 修正済み。`CompressOne` が毎回現在の容量を取得。容量が増える修復・小さくなる修復・削除済み入力をキューテストで確認。 |
| 処理中の追加を成功と表示し、追加件数も不正確 | 修正済み。`AddPath` が受け付けた件数を返し、`WindowProc` の `WM_DROPFILES` が拒否・0件・実際の件数を表示。非同期UIテストで確認。 |
| ワーカーの状態更新と一覧描画の競合 | 修正済み。`CompressOne` はローカル結果を更新し、`PublishItem` と `RefreshListRow` は同じミューテックス下で結果の公開・表示用コピーを行う。独立した実装レビューで追加の指摘なし。 |
| COM終了後にWICオブジェクトを解放 | 修正済み。`Worker` 内のWICオブジェクトを解放してから `CoUninitialize` を呼ぶ。外側でCOMを初期化しないキューテストで確認。 |
| 65,536件で進捗の総数が0になる | 修正済み。`Worker` と `WindowProc` は `WM_APP_PROGRESS` で件数を渡す。実際のハンドラーで32,768 / 65,536が50%、65,536 / 65,536が100%になることを確認。 |
| 修正版ZIP・全CPU版・ソース版の案内が不明確 | 修正済み。`releases/README.md` に5種類の `review-fix` ZIPを明記し、旧配布物を履歴として区別。配布物の最終照合は `BUILD-REPORT.txt` を参照。 |
| 再試行の容量変化・処理途中のキャンセルの検証不足 | 回帰テストを追加。Windows x64・x86でキュー9項目と非同期UI6項目に合格。2枚目の候補処理中に停止し、1枚目の完了・3枚目の未着手を保持した後、残り2枚だけを再開することを確認。 |

テストではAPI境界で設定フォルダーを一時領域へ切り替え、候補通知の同期でキャンセル時点を固定する。上記の進捗境界はメッセージによる検証であり、65,536枚を実際に圧縮した結果ではない。ARM64は本体と両テストをビルドしたが実行していない。既存の位置復元9項目はWindows x64で合格。MSVC・リモートCI・実際のマウス操作・物理モニター構成・ログオフの検証は今回行っていない。

## 修正前のレビュー記録

2026年11月6日。対象は前回の変更。製品コードは修正前の `build/baseline/main.cpp` と比較し、変更行から呼ばれる既存コードも調べた。

## 実機検証

| 操作 | 結果 |
|---|---|
| Aをドロップし、完了後にBをドロップ | Bだけを圧縮。Aの出力が保持された。 |
| 全件完了後に開始ボタンのコマンドを送る | ワーカーは起動せず、出力も増えなかった。 |
| Aを同じパスで再追加 | Aの新しい出力が1個でき、Bの出力は保持された。 |
| Aから生成したJPGを同じセッションで直接ドロップ | JPGも新しい入力として圧縮された。上記の一連の操作で最終出力は計4個。 |
| Aの圧縮開始直後にBをドロップ | Bは一覧に入らず、「追加しました」と表示された。完了後にもう一度Bを投入すると受け付けられた。 |
| 1バイトの破損BMPを57,654バイトの正常BMPに置き換えて再追加 | 上限が1バイトのまま残り、再試行で出力できなかった。 |
| 200,000バイトの破損ファイルを4,496バイトの正常JPGに置き換えて再追加 | 29,465バイトのJPGが生成されて「完了」になった。元画像以下という仕様を超えた。 |

ドロップ検証では、Windows x64で本体のウィンドウプロシージャ、実際のコントロール、非同期ワーカーを使用した。設定の保存先を一時フォルダーに隔離し、非表示のテストウィンドウへドロップと開始のメッセージを送った。実際のマウス操作とファイル選択ダイアログの手動検証は対象外。
